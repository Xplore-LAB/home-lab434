### 踩坑：组探活的返回格式不同

- 单节点 `/proxies/{节点}/delay` → `{"delay": 123}`
- 组 `/proxies/{组}/delay` → `{"节点A": 123, "节点B": 456}`（**扁平映射**）

原 watcher 脚本只认 `d.get("delay")`，探组会直接判失败。已改为：先看有无 `delay` 键，没有就把所有正整数值取 `min()` —— 即"组当前选中那条"的实际延迟。

## 工作流教训

- **长 exec 调用容易被丢弃**：本会话多次出现"Command still running (session xxx)"后 session 直接消失、结果拿不到。取用探测类数据时**优先用 `curl` + 短 timeout 的单条命令**（实测能内联完成），不要用多轮 python subprocess 批量探测。
- **mihomo API 可直接验证实际出站节点**：`/connections` 的 `chains` 字段给出每条连接的完整出站路径，比对比出口 IP 判断"走的哪条线"可靠得多 —— 出口 IP 可能因为节点出口池轮换而误判。
- **provider 节点只能按名出现在 `proxies:` 段**（即静态 `proxies:` 里定义的），订阅里的节点要用 `use:` + `filter` 引入组；写错会报 `'<name>' not found`。
